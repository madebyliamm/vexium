**Why in-function auth instead of gateway `verify_jwt`:** the project signs user tokens with **ES256** (see `/auth/v1/.well-known/jwks.json`); the edge gateway has rejected ES256 tokens before (the editor even has an anon-bearer fallback for it). So functions that must know the user stay `--no-verify-jwt` and verify the token with GoTrue themselves. Never trust `sub` from an undecoded JWT, and never treat the anon key as a user. All functions that read/write billing go through `supabase/functions/_shared/db.ts`, which merges `profiles` + `account_billing` and routes writes to the owning table.
Function versions: run `supabase functions list`.

Deploy: `supabase functions deploy <name>` (add `--no-verify-jwt` ONLY for those marked off). Unit tests for the Step 4 functions: `node --test supabase/tests/site_api.test.ts supabase/tests/auth_gate.test.ts` (Node ≥ 22.18; in-memory fakes, no network). Live abuse suite: `python3 supabase/tests/step4_abuse.py [<worker-url> real]`. Download a deployed copy without Docker: `supabase functions download --use-api <name>`.
Drift check 2026-10-12 (after Step 2 deploy): repo == deployed (spot-checked stripe-checkout, stripe-connect-status via `functions download --use-api`).

## Vercel
Project `vexium` (id in `vercel-proxy/.vercel/project.json`) exists only to terminate TLS for customers' custom domains and forward to the publisher Worker. The `custom-domain` function hardcodes the project id and calls the Vercel API with `VERCEL_TOKEN_KEY`. Note: Cloudflare for SaaS (custom hostnames) could remove this hop — evaluate in Step 3.

### Evaluation: Cloudflare for SaaS custom hostnames vs the Vercel hop (2026-10-13) — recommendation: DO IT, as a dedicated task before Step 12 (LAUNCH); not done in Step 3
- **Measured:** the Worker alone answers on the custom-domain path (`x-forwarded-host`) in **0.30 s** median; the live `www.webre.co` path (browser → Vercel edge fn → workers.dev → Worker) is **0.81 s** median. The Vercel hop costs ~0.5 s per request and is a second vendor to keep alive.
- **Cost (Cloudflare docs, fetched today):** 100 custom hostnames included on every plan; $0.10 per extra hostname per month; hard cap 50,000 on Free/Pro/Business. Custom certs / wildcard hostnames / SNI rewrite are Enterprise-only (we need none of them).
- **What it would replace:** `vercel-proxy/`, the Vercel project, the `VERCEL_TOKEN_KEY` secret and the Vercel-API calls in `supabase/functions/custom-domain` (→ Cloudflare `custom_hostnames` API; needs an API token with *SSL and Certificates: Edit* on the `vexium.ai` zone, stored as a function secret). The Worker needs no change beyond routing custom hostnames to it (a Workers route on the zone; fallback origin = a proxied dummy record).
- **Why not now:** (1) it changes the customer-facing DNS contract — the instructions in the editor's publish panel and the target customers CNAME to — and the only real custom domain (`webre.co`, Liam's) would have to be re-pointed; (2) apex domains (`example.com`, no `www`) are NOT supported by default (needs Cloudflare's advanced "apex proxying") whereas Vercel handles apex via A record today, so there is a feature regression to design around; (3) cert issuance is a two-stage validation (hostname status + certificate status) that needs UI states in the panel; (4) I can't test it end to end without changing DNS on a domain Liam controls. None of that is hard — it just needs a deliberate session with Liam on the DNS side.
- **When:** put it in front of Step 12 (custom domain is a LAUNCH checklist item) — ~1 session. Until then custom domains work as today via Vercel and now also benefit from R2/versioning (v2 over the custom-domain path verified 2026-10-13).
