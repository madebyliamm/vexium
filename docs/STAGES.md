# The stage engine (REVAMP Step 7)

The backbone of the guided flow **PLAN → EXAMPLE → FULL BUILD → TWEAKS → LAUNCH → BUSINESS**. Stages are **explicit state the user controls** (never inferred from a message). Each stage saves an **artifact** the next stage reads, instead of replaying chat history.

Steps 8–13 build the screens and the real prompts on top of this. What exists today: the database, the rules, the AI endpoint *skeletons*, the resume mechanism and a thin studio project page. The per-stage prompts in `ai-chat/stages.ts` are deliberately short placeholders.

## Rules (one source of truth)

`projects.stage` ∈ `plan, example, build, tweaks, launch, business` (default `plan`; existing projects start at `plan`, no data migration).

| artifact kind | made by | client (member) may write | may "keep" while stale | marked stale when upstream changes |
|---|---|---|---|---|
| `plan` | PLAN stage (AI proposes, user edits) | yes | yes | — |
| `style_spec` | EXAMPLE stage (user locks it: `locked: true`) | yes | yes | plan |
| `manifest` | FULL BUILD / TWEAKS (what was built) | **no — platform** | yes | plan, style_spec |
| `launch_checks` | the launch verifier | **no — platform** | **no — re-run** | plan, style_spec, manifest |
| `business_state` | BUSINESS (server-computed) | **no — platform** | no | never (computed from live data) |

* **Going back or staying is always allowed.** Going forward to stage S needs every artifact in `requires[S]` to exist, be **fresh** (not stale) and carry its required flag (`style_spec.locked` must be true wherever the style is required). `business` needs no artifacts, only a live site (`projects.published_version` set).
  `requires`: example←plan · build←plan,style_spec · tweaks←plan,style_spec,manifest · launch←…+launch_checks · business←(live site).
* Saving a new version of an artifact marks the **latest version of every downstream kind stale** (`downstream` = transitive closure of "built from"). The stage the user is in is **never yanked away**; the way forward just closes until they "keep" or redo.
* "Platform" = service role (edge functions / Worker). Reason: a client must not be able to forge a "verifier passed" record or a built-site manifest.
* Versions: each save is a new row `(project_id, kind, version)`; the newest 20 are kept (`max_versions`), each ≤ 256 KB (`max_bytes`).

**The rules live in the jsonb literal in `vx_stage_rules()`** (migration `20261014100000_stage_engine.sql`). `supabase/functions/_shared/stages.ts` mirrors it and `supabase/tests/stages.test.ts` **fails if the two differ**. To change a rule: edit the SQL literal (new migration with `CREATE OR REPLACE FUNCTION vx_stage_rules`), edit `STAGE_RULES` in `_shared/stages.ts`, run both test suites.

## Database

* `projects.stage` — a trigger stops API roles writing it directly (and from inserting a project that isn't at `plan`); only `set_project_stage()` (SECURITY DEFINER) or the service role can.
* `project_artifacts(id, project_id, kind, version, data jsonb, stale, created_by, created_at)` — RLS: SELECT for the owner and **accepted** collaborators; **no** client INSERT/UPDATE/DELETE (privileges revoked). View `project_artifacts_latest` (security_invoker) = newest version per kind.
* RPCs (all re-check access from the JWT; `anon` has no EXECUTE; strangers and "no such project" get the identical error so ids can't be probed):
  * `put_project_artifact(p_project, p_kind, p_data, p_expected_version?)` → `{kind, version, staled[]}`. `p_expected_version` = optimistic concurrency (0 = "none yet"); a mismatch raises SQLSTATE **`PT409`** → HTTP 409.
  * `keep_project_artifact(p_project, p_kind)` → `{kind, version, cleared}`.
  * `set_project_stage(p_project, p_stage)` → `{ok, stage, blocked_by:[{kind, reason}]}`. A refusal is a normal result (`ok:false`), not an error. `reason` = `missing` | `stale` | `flag:locked`; `kind` may be `published`.
* `build_jobs` gained `stage, artifact_kind, finished_at, error, heartbeat_at`. **Column-level grants**: clients may only INSERT `project_id,user_id,status,prompt` and UPDATE `status` (exactly what the old editor does), so only the platform can create a *stage* job. `status` ∈ running/complete/failed.
* Tests: `supabase/tests/step7_stage_engine.sql` (127 checks, always rolls back; the same scenario tables are replayed in `stages.test.ts`).

## AI endpoints (`ai-chat` stage mode — PLAN (Step 8), EXAMPLE (Step 9), FULL BUILD (Step 10) and TWEAKS (Step 11) are real, the other stages are still skeletons)

Additive: only requests with `stage`/`stage_done`/`stage_cancel` reach it; the old editor's paths (incl. the onboarding gate, which the old editor still needs until Step 14) are untouched. Logic is pure + unit-tested (`ai-chat/stages.ts`, `ai-chat/stage-handler.ts`, `supabase/tests/ai_stages.test.ts`); `index.ts` only wires it.

| request (as the signed-in user) | does |
|---|---|
| `{stage, project_id, messages, prepare:true}` — sent to the **build Worker**, which asks ai-chat to prepare | checks access (owner/accepted member) → **input artifacts exist, fresh, style locked** (else `409 stage_inputs` + `blocked_by`) → credit gate (`402 usage_limit`) → creates the `build_jobs` row → returns the Anthropic payload + `job` |
| `{stage_done:{job_id, ok, message, error}}` — sent by the **Worker** when the run ends, with header `x-vx-worker-key` = `STAGE_WORKER_SECRET` (a random secret set as BOTH a Supabase function secret and a Worker secret; **403 without it**, and fail-closed if ai-chat has none: any signed-in user may `prepare` a run themselves, so without this a client could "report" any text and have it saved as an artifact) | job must be the caller's, a stage job, still running → parse the reply, **validate** the artifact, save it via `put_project_artifact` (as platform) → close the job. Unusable output saves nothing and fails the job with a reason |
| `{stage_cancel:{job_id}}` — the studio's Stop button | closes a running job as `Stopped` (idempotent). The Worker notices on its next heartbeat and aborts the generation |

Direct (non-prepare) stage calls get `400 use_worker`.

**Prompt-cache layout:** the cached system block = stage instructions + the stage's **input** artifacts (upstream, frozen, canonical JSON with sorted keys) → byte-identical across turns. The artifact the stage is *editing* (`worksOn`) changes every turn, so it goes in the non-cached suffix with the project name. Tests assert this.

**Output protocol:** the reply ends with `[[ARTIFACT]]` + one complete JSON object + `[[/ARTIFACT]]` (shape spelled out in the cached block); everything else is chat. `normalizeArtifact` drops the `null`s models like to write; `validateArtifact` (`_shared/artifacts.ts`) is the semantic gate; a model can **never** lock a style (`locked` is forced to `false` — locking is the owner's decision).

SSE events of a stage run (via the Worker): `stage_job {job_id, stage}` first → the usual `start/delta/message/done` → `stage_done {ok, artifact:{kind,version,staled}|null, error?}` **last**.

## Resume after refresh

A run keeps going in the Worker after the browser disconnects (stage runs are aborted only when their job row is closed, unlike legacy builds which stop on disconnect). The Worker saves the result server-side (`stage_done`) and stamps `build_jobs.heartbeat_at` every ~8 s. A reloaded studio reads the latest stage job: `running` with a heartbeat < 45 s old ⇒ "Still working…" (polls every 4 s, offers Stop); a `running` job whose heartbeat went silent is dead and is not shown as live; a recent `failed` job's error is shown once.

**Limit (decide in Steps 9/10):** Cloudflare's `ctx.waitUntil` only extends a disconnected request by **30 s**. That comfortably covers PLAN-sized runs (Haiku, ≤ 4k tokens, ~6 s — verified live), but a multi-minute FULL BUILD whose browser disconnects would be cut off after 30 s and its job left to go silent. The long stages need a Queue / Durable Object / Workflow to run server-side; the job + heartbeat + `stage_done` contract here stays the same.

## PLAN stage (REVAMP Step 8) — the first real stage

**Screen** (`studio/src/components/PlanStage.tsx`, plugged into `StagePanel` as `guided`): chat on the left (`PlanChat`), the plan as an editable card on the right (`PlanCard`). Home has a "Start something new" box (`NewProject`): one sentence (or "Not sure yet — talk it through") creates a project at `plan`, opens `#/p/:id` and sends that first message. Pure logic lives in `studio/src/lib/plan-view.ts` (35 tests): card edit helpers, `planProblems` (the server's validator, worded for the owner), `splitLiveReply` (hides the `[[ARTIFACT]]` block while streaming), `historyToSend`, `canRetry`, the revenue calculator maths.

**Who writes the plan:** the AI proposes (stage run → `stage_done` saves a new version); the owner edits the card and presses *Save plan* (`saveArtifact('plan', data, baseVersion)` → a new version). Both are ordinary versions, so editing the plan still marks everything built from it stale. Unsaved card edits keep "Continue" closed ("Save your plan changes first"), are saved before a chat message is sent (the model always sees the owner's edits), and trigger the browser's leave-page warning. A newer version saved elsewhere while the card has unsaved edits shows a conflict notice instead of overwriting either side. The project is renamed to the plan's name once, only while it is still "Untitled".

**Prompt** (`PLAN_BRIEF` in `ai-chat/stages.ts`, model `fast`/Haiku, 4000 tokens): draft the whole plan on the first turn, at most 1–2 questions, short chat, reply in the owner's language; **never invent** prices, customers, testimonials or legal text — what only the owner can supply goes into `launch_checklist`; assumptions go into `notes`; the revenue `scenario` stays `null` until the owner starts the what-if calculator themselves (it is a calculator with editable guesses, never a forecast); the owner's edits are copied back unchanged. `ARTIFACT_SHAPES.plan` carries `notes` (≤ 2000 chars, validated in `_shared/artifacts.ts`).

**Chat history** = table `stage_messages(id, project_id, stage, role, content ≤ 20000, user_id, job_id, created_at)` (migration `20261021100000_stage_messages.sql`; NOT the legacy `ai_messages`, which the old editor replays to the model). Written only by the platform (service role): the user's line when the run is prepared (an identical retry of the same last line is not stored twice), the assistant's line only when the run succeeded (artifact block stripped; "I've updated your plan." if the model said nothing). Unique `(job_id, role)` so a replayed `stage_done` cannot double-write. Best-effort: a failed write never fails a run. Clients can only SELECT (owner + accepted collaborators). The studio reloads it from the server after every run — the server's list is the truth about what was kept. A refused message goes back into the box; an unanswered last message offers "Try again" (re-asks without storing a second copy).

**Resume:** if a run is still going when the page loads (`build_jobs` heartbeat fresh) the chat shows "Still working on your plan…" with the card locked, polls, and reloads the plan + chat when it ends. Stop = `cancelStageRun`.

**Tests:** `studio/test/plan-view.test.ts` (unit), `supabase/tests/ai_stages.test.ts` (PLAN prompt rules + chat persistence, incl. failure/dedupe cases), `supabase/tests/step8_stage_messages.sql` (29 checks, rolls back), `studio/test/browser_e2e.mjs` (guided screen in real Chrome: blank plan → Save → v1/v2/v3, validation message, price + what-if + checklist, dirty-blocks-Continue, history after reload, owner cannot write `stage_messages`, Home "Draft my plan" creates a project and sends the message — the Worker call is **stubbed** in the default run; `E2E_AI=1` sends one real message and prints the plan + reply).

Once topped up, run `E2E_AI=1 node studio/test/browser_e2e.mjs`, read the printed plan, and if Haiku's plans are weak switch `STAGE_RUN.plan.model` to `'build'`.

## EXAMPLE stage (REVAMP Step 9) — the landing page + the style

**What it is:** the owner sees ONE page (the landing page) built from the plan, changes its look with five controls (instant, no AI), and **locks the style**. The full build (Step 10) must obey the locked `style_spec`. Free tier ends here.

**The run** (`EXAMPLE_BRIEF`/`finishExample` in `ai-chat/stages.ts`, model `build` = Sonnet, 24000 tokens, shared craft rules in `ai-chat/craft.ts`): the model writes four files as `<file>` blocks **in this order** — `styles.css` (the `:root` tokens + one Google-Fonts `@import`), `index.html`, `site.js` (`window.SITE` nav/footer for the SDK), `manifest.json` — plus an optional `[[ARTIFACT]]{tone, voice, art_direction}[[/ARTIFACT]]` note. The page has **no forms** (CTAs scroll to in-page anchors) and no invented content. When a *current* `style_spec` exists the brief says: keep its tokens unless the owner's note asks otherwise (so "Build a new version" respects the look the owner picked).

**The style is derived, not trusted** (`_shared/style.ts`): `deriveStyleSpec` reads the spec out of the stylesheet's `:root` tokens; `applyStyleSpec` writes the completed tokens + one font import back (idempotent — a fresh build is never "unsaved"); `manifestWithStyle` makes the manifest colours follow the palette. So file and spec cannot disagree. The finisher forces `locked:false` — **only the owner locks**. Failure = nothing saved, plain-language reason: no page written / stopped before finishing (names the missing file) / file too large / page cut off / page not linked to `styles.css` / style incomplete.

**Files travel with `stage_done`:** the Worker collects the finished `file` events (`cf-worker/stage-report.ts`) and reports them in `stage_done.files` (≤ 40 text files, anything non-text refused). ai-chat saves **files first, then the artifact** (so the artifact version never points at files that aren't there), via the RPC `set_project_files(p_project, p_files)` (migration `20261021110000`, SECURITY DEFINER): merges by name with `||` so other pages are untouched; flat names ending `.html/.css/.js/.json`; ≤ 20 files/call, ≤ 600k chars/file, ≤ 1.5M/call; allowed for the owner, an accepted collaborator, or the platform. The studio uses the same RPC to write the style change of a Save.

**Style engine (`_shared/style.ts`, 44 tests in `supabase/tests/style.test.ts`):** colour maths (`parseColor`, `contrastRatio`, `readableOn`…), presets — `ACCENTS` (9), `FONT_PAIRINGS` (modern, editorial, friendly, elegant, technical, bold), `DENSITIES` (compact/comfortable/airy → `--section-y`), `TONES` (friendly/professional/bold/playful/elegant → tone text, voice, `--radius`), `themeTokens` (light/dark) — and `withVibe(spec, {theme, accent, pairing, density, tone})`, a pure token swap. `readVibe` reads which preset is active (`null` = the model's own choice, shown as "Now using the fonts/tone your page came with").

**Screen** (`studio/src/components/ExampleStage.tsx`, `guided` slot of `StagePanel`): left = the page in a sandboxed `Preview` (Desktop/Phone toggle) with the build checklist above it while a run is going; right = `VibeControls` (Theme, Colour + custom colour, Fonts, Spacing, Tone), readability hints (never forbids a colour), Save/Discard, **Lock this style** ("Save and lock this style" when there are changes — one version), "Want a different page?" (the only place the AI is used again; closed while locked). Pure logic: `lib/example-view.ts` (reading the saved page, `planSave` = what a Save must write, status, progress steps, wording) and `lib/preview.ts` (`buildPreviewHtml`); 34 tests.

* **Preview = `<iframe sandbox="allow-scripts" srcdoc>` — NO `allow-same-origin`.** The model's JavaScript runs in a null origin and can never read the studio's session or call its APIs. The stylesheet is inlined as `<style id="vx-style">`; a vibe change posts `{type:'vx-css'}` to the frame, which replaces that tag's text — **no reload, no AI**. The frame loads the Vertly SDK (`https://vexium.ai/sdk/v1.js?r=2`) with `window.__VX` so the menu/footer render exactly as on a published site, and a small bridge script reports page errors and clicks on links to other pages (→ "built in the next step", the preview never navigates). Messages are accepted only from that frame (`e.source` check).
* **Saving** = `saveArtifact('style_spec', …, expectedVersion)` first (it carries the version guard; a 409 means a newer version exists → conflict notice), then `set_project_files` for `styles.css` + `manifest.json`. The stylesheet is compared with the draft written onto it (not with the saved spec), so a half-finished save still shows as "Unsaved changes" and the next Save completes it. Unsaved changes also trigger the browser's leave-page warning; the status line reads Not built yet / Building… / Unsaved changes / Style locked / Not locked yet.
* **Continue** needs a *locked*, fresh style (blocker "Lock your style first" — shown for both clean and unsaved unlocked styles). The "Save or discard your style changes first" hold exists for the (rare) locked-but-dirty case.
* **A run that is cut off** (browser closed, connection lost): the Worker finishes and saves server-side if it can (limit: `ctx.waitUntil` = 30 s after a disconnect, see *Resume after refresh*); the screen says "The connection was interrupted…" and the page appears on its own when the saved version arrives. Stop = `cancelStageRun`.

**Tests:** `supabase/tests/style.test.ts` (engine), `ai_stages.test.ts` (84: EXAMPLE protocol + finisher incl. every failure), `cf-worker/test/stage_report.test.ts` (files in `stage_done`), `supabase/tests/step9_set_project_files.sql` (30 checks, rolls back), `studio/test/example-view.test.ts` + `preview.test.ts`, and `studio/test/browser_e2e.mjs` section 3e in real Chrome (stubbed Worker stream with live progress + interruption; a seeded realistic page: render, SDK nav, sandbox holds, each control re-skins within a second without reload, Save/Lock/Unlock/"Save and lock"/Discard with exact version numbers and file contents, phone/desktop, other-page link, page error report, 390 px, Continue → BUILD → back). `E2E_AI=1` additionally builds a real page from the real plan, changes the vibe and locks it.

**Not verified with a real model yet** (Anthropic credit empty on 2026-10-21): the live path was checked up to the model call (a real EXAMPLE run through the deployed Worker → ai-chat prepare → "credit balance too low" → clean failure, nothing saved). After a top-up run `E2E_AI=1 node studio/test/browser_e2e.mjs` and look at `/tmp/studio-e2e/ai-example-*.png`.

## FULL BUILD stage (REVAMP Step 10) — the whole site, verified

**What it is:** from the fresh `plan` and the LOCKED `style_spec`, every page of the site is built **in parallel**, the backend (forms, shop, accounts, data lists) is wired from the plan, a **launch verifier** reads the finished site the way a visitor would, and anything it can fix is sent back to the AI for repair. Nothing is written to the project until the very end — **all files are committed in one atomic step** — so a Stop or a crash during the build leaves the project exactly as it was. Paid stage (the paywall itself is Step 14).

**Why a Workflow, not `waitUntil`:** a full build is minutes long; `ctx.waitUntil` gives a disconnected request 30 s. `POST` to the build Worker with `{stage:'build', prepare…}` creates the job (credit gate, input check — `409 stage_inputs` unless plan fresh + style locked), starts a **Cloudflare Workflow** `BuildWorkflow` (instance id = the `build_jobs` id) and answers at once with `{ok, job_id}`. The studio follows the job by polling (`build_jobs` + `build_steps`, every 3 s), so a build survives closing the tab. Same contract as before: job row + heartbeat (`build_jobs.heartbeat_at`, every 8 s while a step runs; the studio treats > 45 s without one as dead) + the job is closed by the platform.

**Who does what** (`cf-worker/*` runs the clock, `ai-chat/*` holds every decision):

| file | job |
|---|---|
| `cf-worker/workflow.ts` | `BuildWorkflow` — steps with retries (`begin` → pages in parallel, concurrency 4 → `verify` → repair rounds → `complete`); on any failure calls `fail` |
| `cf-worker/build-flow.ts` | the flow as pure functions over ports (unit-tested without Cloudflare) |
| `cf-worker/build-ports.ts` | the ports: `aiChatOp` (calls ai-chat `{build_op:{op,…}}` with header `x-vx-worker-key` = `STAGE_WORKER_SECRET`; a 500 carries `detail`), heartbeats |
| `cf-worker/model.ts` | the one place that calls Anthropic (streaming, usage + cache tokens → cost). `ANTHROPIC_BASE_URL` (default api.anthropic.com) exists only so tests can point it at the mock |
| `ai-chat/build-plan.ts` | `planBuild(plan)` → `BuildSpec`: which files, which page does what, nav pages, the backend each page needs (≤ 16 pages) |
| `ai-chat/build-prompts.ts` | the page prompt (cached block: craft rules + plan + style + site map + `styles.css`/kit; suffix: this page) and the repair prompt |
| `ai-chat/site-derive.ts` | **derived, never model-written:** `site.js` (nav/footer from plan), `manifest.json`, `_backend` rules (`deriveBackend` from what the pages actually use), stylesheet finishing (`finishStylesheet`), `assembleSite` |
| `ai-chat/html-lite.ts` | a small HTML parser (no DOM in Deno edge) used by the verifier |
| `ai-chat/verifier.ts` | `verifySite` → `LaunchChecks` + per-page problems; `repairable` picks what the AI may fix |
| `ai-chat/build-handler.ts` | `runBuildOp` (ops `begin | step_start | page_done | verify | complete | fail`), `recheckSite`, `stepInsertRows` |

**Ops** (ai-chat, no user auth, worker key only — an owner JWT sending `build_op` gets `403 forbidden`): `begin` creates the `build_steps` checklist (prepare 0, pages 1.., verify 100, save 101, fixes ≥ 200); `step_start`/`page_done` update rows + cost; `verify` runs the verifier over the pages so far (`MAX_REPAIR_ROUNDS = 2` — after that the report simply lists what is left); `complete` assembles the site and saves it in this order: the platform-only RPC `commit_site_build(p_project, p_files, p_remove)` (migration `20261022100000_full_build.sql`) writes ALL files and removes the stale pages in ONE `UPDATE` (images and other files stay; names/sizes validated, ≤ 80 files, ≤ 6 MB) → the `manifest` artifact (`Manifest{pages, shared_files, backend, cost_cents}`; a new manifest version is what tells the studio "the build is done") → the `launch_checks` artifact (for that manifest version); a failure in between fails the job with "The site could not be saved" and a retry re-does all three; `fail` closes the job with a plain-language reason. Owner-JWT paths: `{stage:'build', build_recheck:{project_id}}` ("Check again" — re-runs the verifier on the saved site, saves a new `launch_checks` version for the same manifest) and `stage_cancel`.

**`build_steps`** (migration): one row per checklist line (`kind` prepare|page|fix|verify|save, `status`, `attempt`, `detail`, `cost_cents`, `output`). `output` (the page text) is **not readable by clients** (column grant — selecting it is a 403); the studio selects `STEP_COLUMNS` only. Rows are inserted in one bulk call, so every row must carry the same keys (`stepInsertRows` — PostgREST rejects mixed keys with `PGRST102`).

**Launch verifier checks** (`LABELS` in `verifier.ts`, each ends as pass/warn/fail in the report): every page built · pages complete + use `styles.css` · scripts close their brackets · every link goes to a real page/file/anchor · images are real files (no stock hosts) · forms connected to a collection · checkout only for products that exist · sign-in/up pages exist when accounts are used · **no placeholder text** (lorem ipsum, "coming soon", TODO/TBD, "your … here", [bracketed] or {{template}} tags, John Doe/Acme, 555 phones, @example.com, "123 Main") · **no invented proof** ("trusted by", "as seen in", star ratings, "award-winning", customer counts, testimonial/logo-wall sections — unless the plan itself says it; percentage / shipping / guarantee / years-in-business claims are warnings) · **only the prices the plan sets** · no empty sections · colours/fonts come from the style tokens · nothing hidden by default (`opacity:0` that only a script reveals — warning) · titles/headings/descriptions · backend rules match the pages · "things only you can supply" (owner items listed, never invented). A `fail` blocks LAUNCH (Step 12); a `warn` is shown. Static analysis only — **no headless browser yet** (see limits).

**Screen** (`studio/src/components/BuildStage.tsx`, `guided` slot): before — what will be built (pages, backend in plain words, "Build my site" + optional direction note); during — the checklist (`lib/build-view.ts` `checklist`/`progress`, pages tick off as they finish, running time, Stop); after — "Built": pages, what was wired up, cost, the report (grouped, with a *Check again* button), and a **page-by-page preview** (`SitePreview.tsx` — same sandbox as the EXAMPLE preview, `allow-scripts` without `allow-same-origin`; links between pages switch the tab). Failure/stop/dead-job banners with a retry. Pure logic is in `lib/build-view.ts` (`buildStatus` → ready|building|built|outdated|failed, `backendSummary`, `reportView`…).

**Testing without Anthropic credit** (`docs/INFRA.md` has the commands): `cf-worker/mock/anthropic.ts` is a stand-in model that writes valid pages (modes: `mock-credit`, `mock-slow`, `mock-flaw` = a dead link on the first try, clean after a repair prompt). Unit tests: `supabase/tests/{build_plan,build_prompts,html_lite,site_derive,verifier,build_handler}.test.ts`, `cf-worker/test/{build_flow,build_ports,model,mock_anthropic}.test.ts`, `studio/test/build-view.test.ts`; SQL `supabase/tests/step10_full_build.sql` (46 checks, rolls back); live Workflow run `scripts/step10_build_e2e.mjs` (41 checks: throwaway users, real Workflow + ai-chat + DB, mock model); Chrome `E2E_MOCK_BUILD=1 node studio/test/browser_e2e.mjs` drives a real build from the UI (188 checks).

**Known limits:** (1) the mock proves plumbing, **not page quality** — nobody has seen a real-model FULL BUILD yet; run `E2E_AI=1 node studio/test/browser_e2e.mjs` after topping up credit and look at `/tmp/studio-e2e/ai-build-*.png`; (2) the verifier is static (parses and cross-checks files) — no headless-browser load, no JS execution, no contrast measurement of the rendered page; (3) generated auth chrome (sign-in/up pages) is English; (4) recurring prices are not sellable online yet (checkout is one-time `products`); (5) in the preview, forms and checkout call the real backend (they are real).

## TWEAKS stage (REVAMP Step 11) — point at it, say what you want
The built site is in `projects.files`; the owner clicks an element in the preview and types ("make this bigger", "say 'Book a call' here"). **A tweak is a patch run, all or nothing.** Edits stay **draft** (only Publish makes them public).

**Request path:** studio chat → build Worker (streaming path, like PLAN/EXAMPLE) → the model answers with `<patch name="…"><find>…</find><replace>…</replace></patch>` blocks (the old editor's format; the Worker applies them to the site's text with the same parser) → the Worker posts `stage_done` with the final text of every touched file → `ai-chat` runs `finishTweaks` (`ai-chat/tweaks.ts`, pure, `supabase/tests/tweaks.test.ts`) → files are saved in one write, then a checkpoint and a fresh launch check. The prompt is `ai-chat/tweaks-prompt.ts` (`TWEAKS_BRIEF`: the site's files + the POINTED AT THIS ELEMENT block: page, tag, visible text, selector); the model never rewrites or creates a file.
**What `finishTweaks` refuses (NOTHING is saved then, the owner gets a plain sentence):** a patch that matched nothing (`patchFailed > 0` — "none of it was made"), a file that isn't editable (`editableFiles`: pages, `styles.css`, `site.js`; never `_backend`, never `manifest.json` directly), a change that adds/removes/renames a form field, sign-up box or buy button (the backend is derived from the forms — "forms are set up in the Plan"; `hooksOf`), and any NEW failing verifier check (a broken link, a missing stylesheet link…). A chat-only reply (a question) saves nothing. If the stylesheet's palette moved, `styleMoved` derives the new `style_spec` (a new artifact version) and `manifest.json` follows the colours (`manifestWithStyle`).
**Checkpoints / undo (`site_snapshots`, migration `20261023100000_site_history.sql`, `supabase/tests/step11_site_history.sql`):** one row per checkpoint (the site's text files), a LINE with one `is_current` row; taken at the end of EXAMPLE, FULL BUILD and after every tweak (`ai-chat/checkpoints.ts`, label = the owner's request); a new change from an earlier point drops the redo tail; max 40 per project; clients read the list (RLS) but never the `files` column. **Moves** — `{tweaks_history:{project_id, action:'undo'|'redo'|'restore', seq?}}` → `moveHistory` (`tweaks-handler.ts`) → platform-only RPC `move_site_history` (replaces exactly the site text files; a page that did not exist then goes away) and supersedes a running tweak. After a move the style, manifest and launch report are brought in step with the restored files: `styleMoved(css, style, {declaredOnly:true})` (only tokens the stylesheet really declares, so a restore never invents tokens), and `manifest.json` is rewritten **only when its colours really differ** (`sameJson`) — an undo must give back the saved text byte for byte.
**Screen** (`studio/src/components/TweaksStage.tsx`, `guided` slot; `TweaksChat.tsx`; pure logic `lib/tweaks-view.ts`; I/O `api/tweaks.ts`): the preview (`SitePreview.tsx` + `lib/preview.ts` — the same sandbox; the bridge script marks `[data-vx-picked]` and reports selector/tag/text/page for a click, never trusting the page), **device frames** (Phone 390 / Tablet 768 / Desktop; `fitScale` rounds DOWN so the frame is never wider than its room), Undo / Redo, a versions list with "Go back to this", the launch report. The root exposes `data-busy` (true while a run or a move is in flight) — tests wait on it; clicks during a move are ignored.
**Testing:** `supabase/tests/tweaks.test.ts` (prompt + finisher + history), `cf-worker/test/mock_anthropic.test.ts` (the mock model's `tweakFor`: `mock-say "…"` anchors on the pointed element's closing tag, `mock-accent #xxxxxx`, `mock-bad-find`, `mock-hook`), `studio/test/{tweaks-view,preview}.test.ts`; live `node scripts/step11_tweaks_e2e.mjs` (61/61, `E2E_TIMING=1` prints each move's timing); Chrome `E2E_BASE=https://vexium.ai E2E_MOCK_BUILD=1 node studio/test/browser_e2e.mjs` (245/245, the mock model is served from a Supabase edge function — `docs/INFRA.md`).
**Known limits:** (1) partial failure inside one patch block isn't reported (a block either matches or the whole tweak is refused); (2) restoring a version from a different build keeps the manifest artifact's page list of the latest build (the recheck tells the truth); (3) a chat-only reply that *claims* a change can't be detected; (4) the pointed element isn't kept across a reload; (5) **real-model TWEAKS quality is unverified** (Anthropic credit empty) — the mock proves the plumbing, not the model's judgement.

## LAUNCH stage (REVAMP Step 12) — go live, inside the studio

**What it is:** mostly NOT AI (`STAGE_BRIEF.launch` stays a placeholder). The `launch` stage shows a pre-launch checklist, the address box and one big **Launch my site** button; publishing goes through the Hosting v2 publisher (`PUBLISH_API`: `/publish`, `/rollback`, `/unpublish`, Bearer = the user's session token). The studio reads the CURRENT draft (`projects.files` + `main_file`) and posts it — the same client-driven path as the legacy editor (no new server code).

**Screen** (`studio/src/components/LaunchStage.tsx`, `guided` slot of `routes/Project.tsx`; pure logic `lib/launch-view.ts` (unit-tested); I/O `api/launch.ts`; QR `lib/qr.ts` via `qrcode-generator` → one SVG `<path>`; the shared fails/warns/open/passes lists are `ReportLists.tsx`, also used by BUILD). `data-status` on `launch-stage`: `blocked` · `ready` · `publishing` · `live` · `live-changes`.
- **Gate (`launchGate`)** — rows `site` (the saved `launch_checks` report; missing/outdated report = "run the final check", *Check again* = `build_recheck`), `content` (owner to-dos from `open_items`, never block), `payments`, `address`. **Blocks:** no manifest, no/outdated report, any failed check, a shop (manifest `backend.products` > 0) without Stripe charges enabled — or Stripe status unknown (retry link) — and a bad address. **Never blocks:** warnings, owner to-dos. While the Stripe lookup is under way the row says "Checking…" (still a blocker).
- **Payments** — `stripe-connect-status` (GET, user token, account-level → `charges_enabled`) is read only when the site sells things and again on `visibilitychange`; `stripe-connect-start` opens Stripe's onboarding and returns to `/studio/#/p/<id>`. Needs a deployed function WITHOUT `--no-verify-jwt`.
- **Address** — `<username>.vexium.ai/<slug>`; the box starts from the project name (`slugFrom`, the publisher's rule), is tidied as the owner types (`cleanSlug`), refused with a reason (`slugProblem`). A live site keeps its address (the box disappears). A connected `custom_domain` wins in `siteAddress`; connecting one is still done in the legacy editor's publish settings (the screen links there). **Offline forgets the address** — the next page load starts from the project name again.
- **Live card** — headline ("You're live! 🎉" right after launching, else "Your site is live"), reachability pill (pings `https://<username>.vexium.ai/__vexium_ping` up to 10 × 1.5 s after a publish so "live" is true when said), URL + Open + Copy, QR, CSS-only confetti (honours `prefers-reduced-motion`), "Update live site" (re-publishes the draft; becomes the main button when `draftIsAhead`), saved versions from `project_deploys` (status `ready`, "Go back to this version" = `/rollback`), **Take offline** (confirm → `/unpublish`, work is kept, back to the checklist), and the hand-off ("Continue to Business" opens once `projects.published_version` is set — the stage engine's own rule).

## BUSINESS stage (REVAMP Step 13) — the numbers (chunk A done; screen, AI partner, digest are chunks B–D)
* **Rule:** the stage needs only a live site (`projects.published_version`). `business_state` is a **platform-only** artifact: nothing a client or the model sends is ever written into it; it is recomputed from rows that exist.
* **Pipeline:** studio → `POST /functions/v1/business-state {project_id, days: 7|30|90 (default 30), refresh?}` with the user's token → GoTrue-verified user, owner or accepted member (else the same 404 as "no such project"), published (else `409 not_live`) → SQL `vx_business_stats(project, days, now)` (service-role only, read-only aggregate) → pure `_shared/business.ts` `buildBusinessState()` → `validateArtifact` → `put_project_artifact` → `{state, version, cached}`. A saved state younger than 60 s with the same period is returned as is (`cached: true`); `refresh` forces a recompute.
* **Sources of truth:** traffic = `page_views` (visitor = `visitor_id`, else `session_id`, else the row; UTC calendar days, today included; the previous period is the same number of days before); orders/revenue = `site_data` collection `transactions` written ONLY by the Stripe webhook (`type: sale` with `status: paid`, and `refund`; amounts are dollars → cents; currencies kept apart: the main currency is the one with the most net revenue, others listed in `other_currencies`); sign-ups = `site_users`; leads = every other `site_data` collection (form entries). `recent` has no emails or names. The site's own host (`<username>.vexium.ai`, custom domain) is dropped from `sources`.
* **Honesty rules (tests enforce them):** `data_level` none / early / ok (ok = ≥ 50 visitors AND ≥ 7 days live, days counted from the first `ready` deploy); `changes.*` and `conversion_rate` are `null` until the earlier number / visitor count is big enough; `vs_plan` (the plan's scenario beside the actuals, scaled to 30 days) is `null` until a week of data; `insights` are plain observations (`id`, `tone`, `text`) computed from the numbers — the AI partner (chunk C) may say nothing the state doesn't contain. Own visits are counted too (noted on the state). No bot filtering yet.
* **Files:** `supabase/migrations/20261024100000_business_stats.sql` · `supabase/functions/_shared/business.ts` (+ `BusinessState` in `_shared/artifacts.ts`, re-exported to the studio) · `supabase/functions/business-state/{handler,index}.ts` · tests `supabase/tests/step13_business_stats.sql` (52 checks, rolled back), `supabase/tests/business_state.test.ts` (28), live `node scripts/step13_business_e2e.mjs` (30, real DB + deployed function, throwaway users). Deploy: `supabase functions deploy business-state --no-verify-jwt`.

## Gotchas
* **Never `RAISE … ERRCODE '40001'` in an RPC PostgREST serves** — the request hangs until the gateway answers 504 (found by the live e2e, ~60 s). Use `PT409` (PostgREST's "`PTnnn` → HTTP nnn" convention). Migration `20261014120000`.
* Inside a SECURITY DEFINER function `current_user` is the owner while `auth.role()` still reflects the caller's JWT — the stage guard trigger uses `current_user`, the RPC access checks use the JWT claims.
* `jsonb` objects print keys ordered by length then bytes — compare JSON, not strings, in tests (`expect()` in the SQL test does).
